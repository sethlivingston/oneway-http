The Body name collision resolution:
- `export type { Body } from "./types.js"` — exports the NOMINAL TYPE (declare class Body)
- `export { Body } from "./body.js"` — exports the NAMESPACE VALUE (factory methods)

- This is valid TypeScript — same name for type + value via declaration merging

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04-01 | Information Disclosure | `serializeBody` visibility | mitigate | serializeBody is explicitly NOT re-exported from index.ts (D-06). If accidentally exported, internal body representation would be accessible. Verify with `grep -c "serializeBody" src/index.ts` returns 0. |
| T-04-04-02 | Elevation of Privilege | `Decoder<T>.fn` field exposed | accept | `fn` is `readonly` and its type is `DecoderFn<T>` — a plain function. Phase 5 uses this intentionally (casts TaggedEntry.decode to Decoder and calls .fn). No privilege escalation risk; callers can construct custom decoders via `new Decoder(fn)`. |
| T-04-04-03 | Tampering | Body type nominal branding broken if `declare class Body` is bypassed | accept | The `declare class Body` pattern provides nominal typing for IDE/compile-time safety, not runtime security. At runtime, any object can be passed as a Body — this is an accepted limitation of TypeScript's structural type system for opaque types without Symbol-based branding. |
</threat_model>
