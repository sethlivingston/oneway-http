<objective>
Add `resolve.alias` to `vitest.config.ts` so Vitest resolves all three package export paths directly to `src/` files without requiring a prior build. Remove all `pretest`/`pretest:*` scripts from `package.json` and update the `verify` script to include an explicit build step.

Purpose: Without aliases, `npm test` silently tests the stale `dist/` output (P13 pitfall). The `pretest` hook was a workaround for this. With aliases active, Vitest resolves imports from `src/` directly — `pretest` build coupling is unnecessary for dev iteration. The `verify` script retains an explicit build to catch bundling failures in CI.

Output: `vitest.config.ts` with top-level `resolve.alias` block; `package.json` with `pretest` scripts removed and `verify` updated.
</objective>

Add a top-level `resolve.alias` block to the `defineConfig()` call in `vitest.config.ts`. The block goes at the top level of the config object (not inside any project) so all future unit tests automatically get source resolution (D-07).

**Critical ordering rule:** The more-specific subpath aliases (`/browser`, `/node`) MUST appear before the bare package alias (`@sethlivingston/oneway-http`) in the alias object. Vite's resolver matches aliases in insertion order — if the bare alias comes first, it will match `@sethlivingston/oneway-http/browser` as a prefix and resolve it to `src/index.ts` instead of `src/browser.ts`.

The target `defineConfig()` call:

```typescript
export default defineConfig({
  resolve: {
    alias: {
      "@sethlivingston/oneway-http/browser": new URL("./src/browser.ts", import.meta.url).pathname,
      "@sethlivingston/oneway-http/node": new URL("./src/node.ts", import.meta.url).pathname,
      "@sethlivingston/oneway-http": new URL("./src/index.ts", import.meta.url).pathname,
    },
  },
  test: {
    projects: [
      // ... existing projects array unchanged ...
    ],
  },
});
```

Use `new URL("./src/browser.ts", import.meta.url).pathname` form (not `"./src/browser.ts"` string) for absolute path safety (D-06 preferred form per PATTERNS.md).

The `createBrowserProject` helper, `parityInclude` constant, and `projects` array are all unchanged. Only the `defineConfig({})` call gains the new top-level `resolve` key.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vitest alias resolver → src/ files | Vite resolves package imports to source files; wrong alias ordering could shadow subpath exports |
| npm scripts → build pipeline | Removing pretest changes when builds run; verify retains build coverage |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Spoofing | Alias ordering in `resolve.alias` | mitigate | Subpath aliases (`/browser`, `/node`) placed before bare alias in object — insertion order determines Vite match priority. Verified by `grep -n 'oneway-http' vitest.config.ts` showing subpath lines before bare alias line. |
| T-02-02 | Tampering | Stale `dist/` picked up when aliases misconfigured | accept | When aliases are correctly configured, Vite resolves directly to `src/`. If aliases fail to load, tests will error on import resolution (fail-loudly), not silently fall back to dist. |
| T-02-03 | Denial of Service | `pretest` removal breaks CI if aliases fail | mitigate | `npm run verify` retains explicit `npm run build` step (D-09). CI uses `verify`, not `test`, ensuring build failures are caught. |
</threat_model>
